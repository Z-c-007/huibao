TECHNICAL NOTES / A技术备用 · 按需展开
删除评论及回复：两个机制，各自有明确职责

多步操作怎样保持完整

事务组织提交与回滚；行锁协调对同一记录的冲突操作

顶层评论 3
↳ 维护回复 4
↳ 维护回复 5

删除原评论时，先删除其回复，再删除原评论。

编号仅为示例。两步删除位于同一个事务中。

TRANSACTION BOUNDARY
锁定原评论→删除回复→删除原评论

正常完成 → 提交

两步变更一起生效，
事务结束后释放锁。

异常传播 → 按规则回滚

撤销本次事务内的变更，
避免只删除了回复。

@Transactional(rollbackFor = Exception.class)
SELECT ... FOR UPDATE

新增回复也锁定原评论，与删除流程协调。行锁不提供旧表单版本冲突检测。

代码位置：ForumServiceImpl 与 ForumMapper.xml；客户端未收到响应不能直接推断数据库已回滚

现象 / 错误线索优先检查可查看的证据
连接被拒绝服务是否启动，地址和端口是否正确启动日志、服务状态、监听端口
code: 401 / 403登录是否有效，是否具备接口权限Authorization、登录记录、权限集合
Redis WRONGPASS客户端与服务端认证配置是否匹配若依日志、Memurai 配置与实际运行值
SQL / 映射异常实际连接、表结构、XML 关联与映射异常根因、执行 SQL、namespace 与 id

本机 Redis 兼容服务可从 Windows 服务、Memurai 日志及客户端 PING 分别确认状态。当前若依的权限错误可能通过 HTTP 200 中的业务 code 表达，需同时检查响应体。

排查顺序：确认实际现象 → 找到证据 → 定位环节 → 修复后重新验证
