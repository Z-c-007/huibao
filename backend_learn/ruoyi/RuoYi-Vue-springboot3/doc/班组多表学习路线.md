# 班组运维关系：六表学习

业务来源：[北三县项目沉淀](D:/GIS_learn/direction/项目沉淀/北三县/项目功能全景_2026-10-31.md)的“1.4.1.1 运维关系配置”。实际项目使用PostgreSQL，本练习使用当前若依的MySQL 8.0；六张learn_ops_表是独立教学模型，不是原项目DDL，也不参与若依账号认证。

## 执行顺序

1. 在DBeaver用有建表权限的账号连接本地ry-vue，打开 `sql/team_multitable_01_init.sql`，按Alt+X执行。只首次执行一次；重复插入遇到主键重复时不要清库。
2. 打开 `sql/team_multitable_02_queries.sql`，每次选中一条完整SQL按Ctrl+Enter。文件内A～G均为只读查询，可反复练。
3. 最后再打开 `sql/team_multitable_03_changes.sql`。按H、I、J等小节分别操作，不整份执行。K是故意报错的练习；错误之后主动执行ROLLBACK。
4. 修改示例默认ROLLBACK，结果可以在同一连接内先查到，回滚后恢复。要永久保留才把对应ROLLBACK改成COMMIT；保留后初始预期及后续操作前提可能变化，需要以实际数据为准。

## 表与数据

|表|角色|初始数据|
|---|---|---|
|learn_ops_user|独立模拟人员资料|1001张三、1002李四、1003王五、1004赵六；1005停用人员|
|learn_ops_section|标段|10一标段、20二标段|
|learn_ops_team|班组|1一班班长张三；2二班班长王五；3三班暂未配置|
|learn_ops_well|阀井|2001/FJ001一标段；2002/FJ002二标段；2003/FJ003一标段；2004/FJ004无标段|
|learn_ops_team_member|班组成员关系|一班张三、李四；二班王五|
|learn_ops_team_well|班组负责阀井关系|一班FJ001、FJ002；二班FJ003|

业务约束：一人最多属于一班，一口井最多由一班负责；班长应为有效用户且在成员名单中。唯一键和外键只能兜底其中一部分规则，不能自动检查所有状态及班长成员一致性。

## 查询验收

|小节|看什么|预期|
|---|---|---|
|A|每张表原始数据|能分清实体记录与关系记录|
|B|六表展开|一班2人×2井=4行，数据没新增，只是查询展开|
|C|错误统计|一班成员数和阀井数都被错误算成4|
|D|先汇总后关联|每班一行；一班2人2井，二班1人1井，三班0人0井|
|E|按张三筛选|一班仍显示完整成员数2；total为1个班组|
|F|班组详情|固定3次查询，主信息+成员数组+阀井数组|
|G|可分配对象|只有正常且未分组的赵六；只有未被负责的FJ004|

D中成员数按“全部已关联人员”计算，不随状态过滤。停用成员是否保留、是否计入有效人数是独立业务口径；选择新成员时G只允许正常人员。

## 写入验收

H新增四班并关联赵六、FJ004；I全量替换一班成员；J全量替换负责阀井。默认回滚，便于重新观察初始数据。

K向一班重复分配已属于二班的FJ003，唯一约束应拒绝。普通SQL语句报错不等于整个事务自动回滚，必须执行ROLLBACK；Java阶段再由Service检测异常及影响行数，并通过有效的Spring事务边界处理。

L只演示删除无成员、无负责阀井的空班组。当前六表模型没有巡检历史表，不能据此认为真实班组删除只需检查两张关联表。

## 第一轮先学到哪里

先执行01，再看02的A、B、C、D。先自己说出每个查询应该有几行，再执行验证。能解释“4行怎样产生、为什么不能直接计数、为什么先汇总能恢复每班一行”后，再看筛选、详情和修改。Java Controller/Service/Mapper接口接入在此之后进行，本轮未新增Java业务接口。
